# Thinking Team：调用侧角色协作

## 目标

`thinking_team` 为调用 Fast Spider 的 ChatGPT/LLM 提供稳定的部门、角色、角色职责、协作流程和协作资料室协议。它只返回配置和协作指导，不创建 Codex、Claude Code 或其他本机 AI 会话。

执行边界：

- `executionTarget = calling_chat_model`
- `providerInvocation = false`
- 当前 ChatGPT/LLM 是唯一主控，负责选择角色、分别分析、处理冲突和输出最终结论。
- `ai_control` 继续负责本机 AI Harness，会话能力与 `thinking_team` 完全分离。

## 部门与角色

当前固定为 9 个部门、17 个角色：

- 产品项目部：产品策略经理、业务流程经理
- 设计体验部：用户体验设计师、界面视觉设计师
- 技术架构部：前端架构师、后端架构师、总架构师
- 程序工程部：前端工程师、后端工程师
- 审计部：代码正确性审计员、测试验收审计员、数据接口审计员、性能稳定性审计员
- 安全风控部：安全风控顾问
- 运行保障部：运维可靠性工程师
- 精算数学部：精算与数学顾问
- 远程顾问：学术顾问

每个角色都有独立 `roleInstructions`。工程角色在 Thinking Team 模式下只从实现可行性角度分析，不因此获得代码写入权限，也不会启动本机 AI。

## MCP Actions

`thinking_team` 支持：

- `team.get`：返回完整团队、流程、资料室和选择规则。
- `departments.list`：列出部门。
- `department.get`：读取一个部门及其角色。
- `roles.list`：列出角色，可按部门过滤。
- `role.get`：读取一个角色、完整职责指令和资料室协议。
- `workflow.get`：读取 `direct`、`parallel`、`review` 或 `full` 流程。
- `workspace.get`：单独读取协作资料室协议。

推荐调用侧按需读取，避免每次获取完整团队配置。例如用户明确点名“总架构师”时直接 `role.get`；点名“审计部”时使用 `department.get`；只有自动选人或首次了解团队时才使用 `team.get`。

## 协作流程

### direct

简单、单视角任务由主控直接完成，不为形式启动角色协作。

### parallel

当多个专业未知项互不依赖时，主控选择通常 2–4 个必要角色，分别从其职责视角分析，然后比较一致点、冲突点和证据缺口。需要唯一跨端技术决策时，再加入总架构师视角裁决。

这里的“并行”表示独立专业视角，不宣称当前调用模型创建了真正独立的模型线程或隐藏 Agent。

### review

已有设计或代码改动进入复核时，各专业角色基于同一事实基线找缺陷，审计角色优先返回可操作问题，最终由主控去重、排序并给出通过/不通过结论。

### full

仅用于跨阶段或高风险任务：产品/流程 → 体验/视觉 → 前后端架构 → 总架构裁决 → 工程可实现性 → 审计 → 安全/运维 → 主控验收。不因任务“看起来复杂”默认拉齐全部角色。

## 协作资料室

复杂多角色任务需要跨 AI 复用信息时，直接使用 `working_context` 的一段普通文本，不再初始化 Markdown Workspace、Plan、Task 或固定文件目录。

推荐文本只保留：目标、当前进度、关键决定、阻塞和下一步。主控先 `working_context get` 取得文本与 revision，合并必要事实后用 `working_context set(expectedRevision=...)` 更新；其他角色只返回结论和证据，由主控统一整理，避免多人争抢写入。

简单任务或当前会话已经记得住的内容不需要写资料室。文本不得保存源码全文、访问令牌、密码、私钥、支付凭证、完整个人信息、聊天全文或原始长日志。

## 选择原则

- 只选择会改变结论、风险判断或验收结果的角色。
- 独立未知项可并行视角分析，存在前置依赖时按阶段串行。
- 总架构师只负责跨端冲突或唯一技术决策。
- 高数据风险、安全风险、发布风险必须保留对应审计/保障视角。
- 最终答案由主控统一形成，不把多个角色意见机械拼接给用户。

## Schema 更新
