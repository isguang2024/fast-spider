# 00 产品愿景

## 1. 产品定义

Fast Spider 是一个面向个人开发者、小型团队和自托管场景的跨平台远程开发与自动化执行平台。它把公网控制面与真实机器执行面分离：Hub 负责身份、权限、路由、任务状态和审计，Node 负责在本机授权边界内执行文件、Shell、Git、浏览器、截图和本地 AI 操作。

Fast Spider 的核心协议独立于 MCP。MCP 只是首个公共 Adapter，后续 Web Console、CLI、REST/SDK 和自动化系统均调用相同的 Capability Engine、策略和审计链路。

## 2. 要解决的问题

现有方案通常落在三个极端：

1. 远程桌面提供完整屏幕控制，但不适合结构化、可审计的 AI 工具调用。
2. 通用内网穿透暴露端口或协议，授权粒度过粗，容易扩大攻击面。
3. AI 编程工具通常只控制本机或单个 Provider，难以安全管理多台异构机器和多个 Workspace。

Fast Spider 提供中间层：只暴露明确能力，不暴露任意端口；只访问用户授权 Workspace，不把绝对路径暴露给远程客户端；每项操作都有身份、权限、状态、事件、取消和审计语义。

## 3. 目标用户

### 3.1 MVP 主用户

- 单人 + AI 的开发者。
- 拥有一台公网服务器和若干 Windows/Linux 开发机的自托管用户。
- 需要让 GPT、Claude、Codex 等客户端访问不同机器项目，但不愿开放 SSH、SMB 或任意端口的人。
- 需要可观察、可取消、可复核自动化执行的人。

### 3.2 后续用户

- 2 至 20 人的小团队。
- 需要集中管理构建机、测试机、浏览器测试机的团队。
- 希望用 SDK/CLI 接入内部自动化的用户。

MVP 不以大规模多租户 SaaS 为目标。

## 4. 核心价值

### 4.1 安全边界清晰

Node 只出站连接；Hub 不直接执行；Node 本地进行最终权限裁决；远程请求只使用 opaque machineId/workspaceId；文件、命令、Git、浏览器和 AI Session 分别授权。

### 4.2 能力统一

本地和远程入口共用同一能力实现。MCP、Web Console、CLI 和 Local Bridge 不各自维护一套文件或 Shell 逻辑，避免语义漂移和权限绕过。

### 4.3 可运营但不过度设计

Hub 是一个 Go 模块化单体，Web 静态资源内嵌，SQLite WAL 保存控制面数据，Artifact 先落本地磁盘。单机部署、备份、升级和恢复优先于横向扩展。

### 4.4 适合 AI 协作

工具数量稳定；长任务通过 Job 和事件流表达；结果包括结构化摘要、Diff、日志与 Artifact；AI 可以发现能力，但不能绕过权限，也不能在无边界条件下互相递归调用。

## 5. 产品原则

1. Hub 是控制面与路由层，不触碰节点真实资源。
2. Node 是执行面与最终权限裁决者。
3. 默认拒绝，显式授权。
4. 不提供任意 TCP 转发。
5. 不把 localhost 视为天然可信。
6. 所有高风险操作必须可见、可审计、可取消、可超时。
7. 协议与 MCP 解耦。
8. 优先单进程、单数据库、少组件。
9. 扩展点必须真实服务于阶段路线，不为假设规模预建复杂设施。
10. UTF-8、结构化错误和版本化契约是基础要求。

## 6. 成功指标

### Phase 1–3 可用性指标

- 新 Node 在 5 分钟内完成安装、配对和首次上线。
- Node 无任何公网监听端口。
- 授权 Workspace 后，MCP 客户端可稳定读取、搜索、编辑并查看 Diff。
- Shell 长任务可以持续读取日志，并在取消后终止完整进程树。
- Node 断线重连不会重复执行已完成的写操作。
- Workspace 禁用后，旧 Session 无法继续访问。

### 安全与运维指标

- 每个远程操作可以追溯到用户、客户端、机器、Workspace、Capability、Action 和 requestId。
- 设备吊销在下一次请求或连接重建时立即生效。
- 敏感字段不进入普通日志。
- 单机 Hub 可以通过复制数据库、配置和 Artifact 目录完成一致性备份与恢复。
- 日志、事件和 Artifact 均有容量及保留策略，不允许无限增长。

## 7. 非目标

MVP 不实现实时远程桌面、音频、通用鼠标键盘远控、P2P 打洞、任意 TCP 转发、移动端客户端、Kubernetes、大规模多租户、复杂消息队列、自动提权、隐蔽运行或 AI 无限递归调用。

## 8. 产品阶段

Phase 0 固定产品边界、协议、安全模型和技术选型；Phase 1–4 优先完成工作区、文件、Shell、Git、任务和事件能力；Phase 5–6 加入浏览器、截图、Local Bridge 和 Codex Adapter；Phase 7 收敛简单运维、备份恢复和版本检查；Phase 8 把安全/故障回归与真实 E2E 收成可重复 Release Gate。自动更新、安装包、托盘、长 soak 和公开发布流水线只有出现真实需求时再单独立项。
